## Option 2: use BYOK on the free plan

BYOK means “bring your own key.” Zush supports Gemini, Groq, OpenAI, and Claude provider keys. BYOK uses the same 50-renames FREE allowance; PRO removes the Zush app limit, while provider quotas and charges remain separate.

BYOK is useful when you want to:

- choose a specific supported provider or model;
- keep provider billing separate from the desktop app;
- use an existing organization account or quota;
- compare model output while keeping the same Zush preview, Template, monitoring, and undo workflow.

There is no honest universal “cost per file.” Provider cost depends on the model, input size, extracted text or image payload, output length, cached tokens, and current provider pricing. Check the provider's live pricing page and measure a representative batch before estimating monthly cost.

### Reproducible BYOK cost estimate

For a 20-file sample, record:

1. provider and exact model name;
2. input and output tokens or billed units;
3. image or document processing charges, if separate;
4. failed or repeated requests;
5. total provider charge shown in the provider dashboard.

Then calculate:

`estimated monthly provider cost = sample cost ÷ successful sample files × expected monthly files`

This is an estimate, not an independent benchmark. Model pricing and file complexity can change the result.

For setup instructions, use the [Zush BYOK guide](/docs/byok).

## Option 3: use Zush Offline AI with Ollama

Offline AI runs a compatible model through Ollama on your computer for supported analysis. It avoids sending the file to a managed cloud model, but it requires a model download, local disk space, memory, and enough compute for acceptable speed.

The practical trade-offs are hardware-specific:

- a smaller model usually downloads and runs more easily;
- a larger model may require more memory and take longer;
- image, document, audio, and video workflows do not have identical requirements;
- local output should still be reviewed before applying a batch.

Zush keeps the same preview and undo workflow across Cloud AI, BYOK, and Offline AI, so you can compare modes with the same copied files. See the [Offline AI file renamer guide](/offline-ai-file-renamer) for the current setup path.

## Option 4: open-source or DIY local renaming

Technical users can build a free local path around Ollama. One example is the GPL-3.0 [`ozgrozer/ai-renamer`](https://github.com/ozgrozer/ai-renamer) command-line project. It is separate from similarly named commercial desktop products.

Before using any CLI on real files, verify:

- whether it previews changes before renaming;
- how it handles duplicate or invalid filenames;
- whether it preserves file extensions;
- whether it produces a reversible log;
- which formats the current version actually reads;
- which local model and prompt were used.

A minimal DIY script needs file extraction, model calls, filename sanitization, collision handling, retry logic, extension preservation, logging, and rollback. If those safeguards are missing, “free” shifts the cost from money to development and recovery time.

## How to choose the free path

Choose by constraint:

- **Fastest start:** Zush Cloud AI, because no provider key or local model is required.
- **Provider control:** Zush BYOK with a supported key.
- **On-device analysis:** Zush Offline AI with Ollama and compatible hardware.
- **Terminal-first experimentation:** a maintained open-source CLI on copies of non-critical files.
- **Learning project:** a DIY script with an explicit rename log and rollback step.

For most people, the first decision is not which model is theoretically best. It is whether the proposed filenames are useful, reviewable, and reversible on the files they actually manage.
