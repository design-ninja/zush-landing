Quick answer: clear duplicates before you rename, not after. Renaming first gives every copy its own polished name and erases the `(1)` and `copy` suffixes that were the only visible sign of which file was the spare. In [Zush](/), both happen in one batch: copies are matched by content before anything is analyzed, and you choose whether they stay, get marked in the name, or go to the Trash.

This post is about the order of the two jobs. The settings themselves are covered in [duplicate file handling](/docs/duplicates).

## What renaming first costs you

Take a Downloads folder with `scan_0041.pdf` and `scan_0041 (1).pdf` in it. Rename it with any content-aware tool and you end up with two files called something like `Invoice 2026-1047.pdf` and `Invoice 2026-1047 1.pdf`.

Three things just went wrong. The names no longer tell you which file is the spare, because both describe the same invoice equally well. The suffix that did tell you is gone. And you paid to analyze the same invoice twice.

The last point is the easy one to miss. Content-aware renaming reads each file, which costs credits, an API call on your own key, or local compute and time. A folder that is a third duplicates costs a third more than it should, every time you process it.

There is a quieter problem too. The ` 1` at the end of `Invoice 2026-1047 1.pdf` is a collision suffix: the renamer added it because the name was taken. It looks exactly like the suffixes you were trying to get rid of, so the folder now carries a fresh set of copy-looking names, some of which are real copies and some of which are just two different files that happened to earn the same name.

## The same folder, both orders

Picture 240 files where 60 are byte-for-byte copies of others in the folder. That leaves 180 distinct files.

| | Rename first, deduplicate later | Deduplicate in the same batch |
| --- | --- | --- |
| Files sent for analysis | 240 | 180 |
| Copies after the batch | 60, each under a good name with a collision suffix | 60, kept, marked, or in the Trash, your choice |
| Clue to which file is the spare | Gone. Both names describe the same content | The `Duplicate of` label in the preview, and the mark if you chose one |
| Passes over the folder | Two, often in two different tools | One |
| What Undo reverts | Each pass separately | Renames and removals together, from one Activity history |

The cost row is the one people notice. The clue row is the one that hurts later, because a pair with no clue has to be resolved by opening both files, comparing dates, or guessing.

## Matching by content, not by name

A name-based check would pair `scan_0041.pdf` with `scan_0041 (1).pdf` and stop there. It misses a copy that someone renamed, which is exactly what tends to happen, and it wrongly pairs two unrelated downloads that a browser numbered on the same day.

Content matching compares the bytes. Two files are a pair when they hold exactly the same data, whatever they are called and wherever they sit in the batch. That catches the copy you renamed to `invoice final.pdf` six months ago, and it refuses to pair two different PDFs that happen to share a name pattern.

In Zush it is a Template setting, under Processing, and the same switch sits behind the Duplicates button in AI Rename:

![Zush AI Rename with duplicate detection on: three copies are unchecked and labelled with the file they match](/images/showcase/macos/duplicates-keep-light.webp)

Once it is on, every copy in the batch is labelled with the file it matches, and none of the copies are sent to the AI. That is where the 240 becomes 180.

## Choosing what happens to the copies, by folder

The Copies setting has three options: Keep as is, Mark in name, and Move to Trash. The [docs](/docs/duplicates#what-happens-to-the-copies) describe each one. Which to pick mostly depends on the folder, so here is how they map:

| Folder | Copies setting | Why |
| --- | --- | --- |
| Downloads, Desktop, a scanner output folder | Move to Trash | The copies are accidents: an attachment saved twice, a file downloaded again because the first one was hard to find. Undo covers you until the Trash is emptied. |
| A shared or synced folder | Mark in name | A file someone else put there is not yours to delete. A marked copy sorts next to its original and can be cleared later by whoever owns it. |
| An archive you have not opened in a year | Keep as is | Some pairs are deliberate, such as a contract filed under two clients. Read the labels first, then rerun with a stricter setting. |
| A folder watched by Monitor | Mark in name, until you trust it | Monitor applies the Template without a preview, so Move to Trash on a watched folder deletes new arrivals unattended. |

![Zush with Mark in name selected, showing copies named after their originals with DUPLICATE appended](/images/showcase/macos/duplicates-mark-light.webp)

If a folder's names are already fine and only the copies need to go, the built-in Remove Duplicates Template keeps every filename and moves the copies to the Trash.

## Already renamed first? Recovering the pairs

If the folder was renamed before anyone thought about copies, the content check still works, because it never looked at names. What is missing is the evidence for which file to keep. Some places to get it back:

1. **Activity, if the rename was done in Zush.** Activity lists each processed file with its original name and its new one. Look up both files of a pair and the one that used to be `scan_0041 (1).pdf` is your spare.
2. **The folder each file is in.** A copy sitting in Downloads next to an original filed under a client folder is almost always the one to drop.
3. **Date Added on a Mac.** In Finder's list view, the Date Added column shows when a file arrived in its current folder. The later arrival is usually the second download.
4. **Undo, as a last resort.** Activity can restore the old names. Undo the rename, run one batch with duplicate detection on, and the copies are handled before anything is analyzed again.

Then run the batch with Mark in name rather than Move to Trash. With the old suffixes gone, a mark you can review is safer than a deletion you cannot see coming.

## Doing it in the right order with separate tools

The order holds whatever software you use. If you clean copies with a dedicated duplicate finder and rename with something else, run the duplicate finder first and empty its results before the renamer touches the folder. The other way round, the renamer's collision suffixes make the duplicate finder's report harder to read, and every copy has already been analyzed once.

For a check without installing anything, [finding duplicates by hash](/blog/find-duplicate-files-by-hash) lists exact copies from Terminal or PowerShell without changing a file.

## Where exact matching stops

Byte-for-byte matching is exact, which is its strength and its limit. Two scans of the same sheet, a photo and its edited version, or a document saved as both `.docx` and `.pdf` are different files as far as the bytes go, so they are not paired. Those still need a human look; the posts on [duplicate scanned PDFs](/blog/duplicate-scanned-pdfs) and [duplicate photos on a Mac](/blog/find-duplicate-photos-mac) cover them.

For the ordinary case, where a file was copied, downloaded twice, or synced back from a drive, exact matching does not produce false pairs, and doing it before the rename is what keeps the result readable.

For the Mac-specific alternatives, including Finder and the Photos Duplicates album, see [how to find and remove duplicate files on Mac](/blog/find-remove-duplicate-files-mac).

## FAQ

### Does the order matter if my Template only uses dates or counters?

Less, because nothing is analyzed and there is no cost to save. The clue problem stays: after a counter rename, `scan_0041.pdf` and `scan_0041 (1).pdf` become two numbered files with nothing to show which is the copy.

### What happens if I rename first and deduplicate afterwards?

Detection still works, because it compares contents rather than names. What you lose is the information in the old names, so deciding which file to keep means checking Activity, dates, or locations instead of reading the suffix.

### Do duplicate files use AI credits?

No. Copies are identified before analysis and are never sent to the AI, so they cost the same whether you keep, mark, or trash them.

### If I run the same folder again next month, are the old copies caught?

Yes, if they are still there. Detection runs on every batch, and a copy that was kept or marked last time is still byte-for-byte identical to its original.

### Does this work the same way on Windows?

Yes. Copies go to the Recycle Bin rather than the Trash, and Activity and Undo work the same way.
